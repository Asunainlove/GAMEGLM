## 决策与限制

1. **deferred_ops 决策（契约 §0/WP04 规避）**：`choose_option` 只直接施加 main 既有操作（`set_flag`）；`relation_delta` 不写持久层，而是返回 `AppResult.value = {"deferred_ops": [{"op": "set_relationship", "char_id", "dim", "value"}]}`，value 已按 `state.relationships` 当前值（缺省 0）钳制 0..100，由 WP04 合并后的集成层经 `GameState` 统一施加。仅含 relation_delta 的选项不创建 patch（零提交）。
2. **store 注入模式**：`store: Object = null`，null → `GameState` autoload（已由测试验证回落路径，测试后回写 flag=false 清理）。store 交互全部走未类型化 `.call()`（`begin_patch`/`set_flag`/`add_item`/`commit`），不对 `StatePatch` 类型化变量调用新操作；DuckStore 替身存于测试实例字段保活（Callable/注入只持 ObjectID 的教训）。apply_effect_step/complete_event 无 state 参数，expected_revision 经 store 的 `snapshot()` 查询当前 revision（has_method 守卫，缺失时 0）；choose_option 按契约字面使用 `state.revision`——调用方须保证二者一致。
3. **source_id/flag 命名采用任务字面格式**：`"event_%s_choice" % event_id` 等，event id 本身已含 `event_` 前缀（契约 §7），故派生 ID 呈双前缀形态（如 `event_event_prologue_landing_choice`、done flag `event_event_prologue_landing_done`）。`available_events` 与 `complete_event` 使用同一模板，模块内自洽；跨包消费方必须经由 EventRunner 的 API 读写，不得自行拼 ID。
4. **选项匹配语义**：`option` 参数仅按 id 从 `step.options` 中选取权威定义（含 set_flag/requires_trust/relation_delta），传入 option 上的其他字段不参与结算；ID 不属于该 step → 失败 `unknown_option`（测试中相应断言按此语义构造）。
5. **JSON 解析用 `JSON.new().parse()`** 而非 `JSON.parse_string()`：后者对坏 JSON 打印引擎错误，会被 GUT 记为 "Unexpected Errors" 而误判测试失败；实例方法经返回码报错，无控制台噪声，失败码仍为 `invalid_event_file` 并含行号与文件名。
6. **最小校验口径**：id/kind 为非空字符串、steps 为非空数组、每个 step 为对象且 `type ∈ {line, choice, effect}`，与任务口径一致并加严 steps 非空（对齐 schema minItems 1）；完整 jsonschema 校验属 ContentDB/离线脚本职责。
7. **DialogueBox 表现层约束**：不触碰持久状态，只发 `finished`/`option_chosen` 信号；选项按钮移除采用 `remove_child`（同步）+ `queue_free`，保证信号触发后计数即时正确且不在信号发射中销毁按钮；空行列表立即发 `finished` 并保持隐藏。灰盒文案为原创中文（「？？？」/「……」/「选择」提示）。
8. **限制**：未接 ContentDB（WP01）与事件编排层（WP11/WP14），本包只交付纯逻辑 + 场景与信号契约；`load_events_from` 非递归（对齐 `data/events/*.json` 布局）；重复事件 id 不在加载器去重（属 ContentDB 交叉校验职责）。测试对 autoload 的 null-store 探测会在运行期使 autoload revision +2（含清理 patch），不影响任何既有测试（无测试依赖 autoload 可变状态）。
