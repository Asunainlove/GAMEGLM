## Decisions and limitations

- New relationship records are created with the full v1 dimension shape `{"affection": 0, "trust": 0, "ideology": 0}` before writing the requested dim. Reason: frozen `SaveCodec._validate_relationships` requires `affection` and `trust` on every record; lazy single-dim records would make snapshots unsavable. Observable semantics match `Relations.get_dim` default 0 (WP09).
- `record_battle_outcome` uses the single contract-named failure code `invalid_battle_result` for both a non-member `result` and negative `turns`; `battle_id` validation uses `invalid_battle_id` following the existing `invalid_item_id`/`invalid_flag_id` naming pattern.
- Handlers keep `typeof` defenses (e.g. `invalid_relationship_value`, `invalid_ideology_delta`) that are unreachable through the typed chain API, mirroring the existing handler style and guarding untyped op dictionaries.
- Migration applies after checksum verification because an older writer's checksum covers its own un-migrated body; identity-for-v1 keeps every baseline test green.
- The migration table currently contains only the v1 identity entry; no real v1->v2 transform exists yet (by design this packet keeps `save_version = 1`).
- Golden fixture is the byte-exact `encode_snapshot()` output (single line, no trailing newline) so decode -> re-encode byte equality is assertable; regenerate via the committed `tests/golden/generate_golden_v1.gd`.
- `content_hash` remains a generator-supplied provenance string until ContentDB integration supplies the real gameplay content hash.
