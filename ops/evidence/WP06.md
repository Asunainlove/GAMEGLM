## 决策与限制

1. **静态/实例双 API**：任务与契约 §5 要求 `validate_placement`/`try_build` 为 `static`，但 GDScript 静态函数无法访问实例成员，`var cell_lookup` 随之无法在静态路径生效。故：静态入口保持冻结签名、仅凭 snapshot 的 `chunk_deltas` 判破坏；实例入口 `check_placement`/`attempt_build` 复用同一实现核心并注入 `cell_lookup`（供 WP03 世界等有地形知识的调用方使用）。
2. **cell_lookup 约定**：`Callable(chunk_id: String, cell: Vector2i) -> Dictionary`（格定义；`destroyed == true` 拒绝；非 Dictionary 返回值忽略）。注入 lookup 与已记录 delta 取并集——已记录的 destroyed delta 不可被 lookup 的完好结论覆盖。
3. **原子单 patch**：try_build 校验全部通过后，单个 patch 依定义顺序 `remove_item`×N + `place_building`，`source_id = building_<building_id>_<x>_<y>`、`expected_revision` 取自传入 state 的 `revision`，commit 结果透传；原子性由 GameState 的“深拷贝校验、一次 revision 递增”保证。重复 source_id 由 GameState 幂等（`already_applied`）。
4. **inputs 形状**遵循冻结 schema（`building-recipe.schema.json`：数组项 `{item_id, count}`）；count 接受 int/float（JSON 数字）并归一为 int 再进 patch；同名物品条目聚合求和后统一检查，失败 message 列出全部缺失物品。
5. **限制（source_id 负坐标）**：负格坐标会令 `building_x_-1_2` 含 `-`，被 `GameState._is_stable_id` 拒为 `invalid_source_id`。负坐标建筑在协调者调整 source_id 方案前会在 commit 阶段失败（校验阶段不拦）。
6. **限制（autoload 污染）**：唯一触碰真实 autoload 的用例使用唯一 ID（资金 `wp06_test_fund_autoload_build`；建筑 `anchor_block` @(40001,40002)）。已核实其余测试均自建 GameState 实例、不读 autoload，且每次 GUT 运行都是新进程，污染被限制在单次运行内。
7. **校验顺序**固定为 `invalid_building` → `building_cell_occupied` → `cell_destroyed` → `no_nearby_structure`，try_build 在材料检查之前完成全部放置校验（有用例锁定该顺序）。
8. **相邻规则**：非 anchor 建筑要求同 chunk 内任意已放置建筑 Chebyshev 距离 `max(|dx|,|dy|) ≤ 3`；跨 chunk 邻居永不计入（有用例锁定）。
9. DuckPatch/DuckStore 测试替身镜像 `GameState.commit` 语义（幂等 → revision → 空 patch → 逐操作深拷贝应用），符合契约 §0 对并行包本地替身的要求；未引用任何其他工作包的文件。
