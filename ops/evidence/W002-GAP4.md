## 实现

**任务 1（精炼闭环，D3）**
- 新建 `src/crafting/crafting_service.gd`（`class_name CraftingService extends RefCounted`，纯逻辑）：
  - `available_recipes(state, defs, powered_ids: Array[String]) -> Array[Dictionary]`：
    仅遍历 `placed_buildings` 中 `powered_ids` 命中的建筑；`recipes` 数组优先、
    单 `recipe` 兼容回退（`_recipes_of`）；同建筑同配方去重；元素
    `{building_id, recipe}`，recipe 为深拷贝。供电判定由调用方算好传入
    （本模块不 import PowerGrid，保持纯逻辑）。
  - `recipe_inputs(recipe)`：归一化为 `[{item_id, count}]`，支持可选第二输入
    `extra_input_item_id/extra_input_count`（决策 1）。
  - `can_craft(state, recipe)`：聚合输入后逐项比对 inventory；非法配方恒 false。
  - `craft(state, building_id, recipe, store = null)`：配方形状非法 →
    `recipe_unavailable`；材料不足 → `insufficient_item`；满足则单 patch
    （`remove_item` 输入 + `add_item` 输出）原子提交；source_id =
    `crafting_<building_id>_<revision>`（同 revision 重放经 applied_patch_sources
    幂等吸收，实测 `already_applied` 且不重复扣料）；store 为 null 委托
    GameState autoload（契约 §0 注入模式）。
- `data/content/buildings.json`：resonance_loom 改用 `recipes: [mist 配方,
  shock_trap 配方]`；dust_refiner 单 `recipe` 保留（兼容形态共存验证）。

  强制成对出现），其余冻结不变。

## 供电布局计算（D2）

- 需求：精炼器 4 + 织机 5 + 稳定塔 6 + 回响舱 8 = **23**。
- 供给：工坊 16 + 锚块 2×n。
- **4 锚块 + 工坊 = 24 ≥ 23 ✓**（集成测试按 4 锚块→工坊→精炼器→织机→稳定塔→
  回响舱顺序成行放置，PowerGrid 按输入序分配，锚块供给先累积；全部获电、
  `echo_chamber_active`/`pylon_stabilized` 置位、`unpowered_building_ids` 为空）。
- 边界锁定：3 锚块 + 工坊 = 22 < 23，恰好差 1——集成测试证明此布局下回响舱
  断电（requires_room 已满足，纯供电不足），平衡不再是"数值上不可能"。
- 回响舱 requires_room：行式布局同 chunk 4 连通成房间，满足"位于任一房间内"。

## 决策与限制

1. **配方双输入的表达（关键决策）**：任务书终案写"recipes 元素同 recipe 形状"，
   但契约 §7 冻结的织机第二配方是 **2×lumen_shard + 1×resonant_core → 1×shock_trap**，
   单输入形状（input_item_id/input_count）无法表达。裁定：recipe 形状增加
   可选第二输入对 `extra_input_item_id/extra_input_count`（ContentDB 校验强制
   成对、stable id、正整数；schema anyOf 同步），元素其余形状与既有 recipe
   完全一致——既满足"元素同形状"的兼容意图，又逐字落地 §7 双输入。
   §7 数值未改，仅表达载体扩展。
2. **ContentDB/schema 的改动授权**：允许路径清单未列 `src/content/**`，但任务
   1.2 明示"ContentDB 校验同步支持（refs 检查两种形态）"——若不改，新增
   `recipes` 字段会被 `_reject_unknown_fields` 拒收导致 bootstrap 失败。
   改动最小化：BUILDING_FIELDS + `recipes`、RECIPE_FIELDS + 两个可选
   extra_input 字段、`_validate_building` 校验 recipes 数组、`validate_refs`
   经统一 `_building_recipes()` 检查两种载体。schema 文件修订为任务书明示授权。
3. **契约 §7 的 power_supply 数值**：§7 记载 anchor_workshop power_supply=10；
   本包按任务书裁定（D2，协调者已审核确认）改为 16 并给 anchor_block 基础
   供能 2。§7 的建筑/物品 ID 集与配方数值均未动；建议协调者在下次合同修订
   时把 §7 该两处数值同步（16 与 2），避免文档与数据长期漂移。
4. **HUD 只读约束保持**：BuildBar/配方区全部数据来自注入 provider；HUD 仅发
   `build_selected`/`craft_requested` 信号，落账全在集成层；两次"点击后重渲染"
   均用 `call_deferred` 避免信号发射过程中 `free()` 发射按钮（battle_scene
   同款教训）。
5. **husk 遭遇的回写断言选 mist**：shard_husk 的 drops 含 1×shock_trap，会与
   回写量恰好抵消；集成测试改用无任何掉落来源的 sedative_mist 做确定性断言
   （trap 回写由单元层 victory/defeat 用例覆盖）。
6. **Godot 教训落实**：HUD provider/替身宿主（CatalogHost 等）全部存测试实例
   字段保活；`assert_signal_emitted_with_parameters` 第 4 参是 index 而非文案，
   传文案会把 String 当 index 触发引擎错误（实测两次后改为无文案调用）。
